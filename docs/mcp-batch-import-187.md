# MCPによる紙記録の一括取込（#187）

`submit_record_candidates_batch` は、AIアプリが読み取った最大10件を既存の管理者確認待ち候補として送信します。PDF原本は受け取らず、記録の作成・承認は行いません。各行に一意な `request_id` を与え、通信断や失敗後の再試行では同じIDと同じ内容を使います。送信済み行は二重作成せず元の結果を返し、IDを異なる内容に使うと `request_conflict` を返します。既に承認等で候補がなくなった場合は `already_processed` です。

各行は単件取込と同じ正規化・確認質問を使います。不明点がある行は質問待ちとなり、他の行の処理は継続します。内容が不正な行、件数制限、同一内容の候補をそれぞれ区別し、不要な入力・本文はログへ出しません。重複判定は同一事業所・同一送信者の読み取り結果のメタ情報と値の完全一致であり、警告・信頼度・ファイル名は比較しません。別人の送信や微妙に異なる読み取り結果は検出できず、同じ内容でも別の記録である場合があります。`possible_duplicate` は確認を求める候補であり、利用者が送信を明示した場合だけ `allow_duplicate` を使います。

`find_import_shift_candidates` は利用者が確認した利用者IDと日時から、シフト参照が許可された範囲の重なりを候補として返します。取消済みは除き、JSTの業務日・ページングを使用します。複数候補を自動選択せず、記録やシフトへの紐付けは行いません。参照の事業所別設定と権限が必要です。

登録は既存の `submit_mcp_candidate` のOAuth・本人・事業所・件数・停止制御を再利用します。担当制の候補送信は従来どおり拒否し、対象利用者を推測して認可しません。候補と再送IDの対応には非公開schemaのダイジェストだけを保存し、原本や記録本文を複製しません。新規RPCとMCP関数はmigrationを先に適用し、アプリ側の稼働を確認してから関数を配備します。機能有効化は事業所管理者の確認が必要です。
