# MCPの個人情報提供条件と停止設計（Issue #169）

状態: 停止方針は2026-10-27に承認済み。停止制御はPR #192でmainに統合し、同日ステージングと本番にmigrationを適用済み。提供条件のGo判定は未実施。対象は接続済みの紙記録候補取込と、今後のMCP機能。本番接続先と配備ソースの照合は[PR #191](https://github.com/shougayaki-1/care-record/pull/191)に記録した。外部サービスの契約・設定と事業所ごとの承認状況は未確認。実際の配備証跡と残件は「検証とロールアウト」に記載する。本書の記載は法令適合や提供許可を意味しない。[システム方針](system-decisions.md)が優先する。

## 判定

AI記録インポートは、データ処理条件、保存地域、ログ保持、利用者説明の確認が完了するまで機能フラグで無効とする（システム方針 §9）。本調査ではこれらの成立を確認できておらず、個人情報を扱う新たなMCP機能は **No-Go**。既存候補取込についても事業所ごとの提供条件の確認が必要である。`AI_IMPORT_ENABLED` は既存のアプリ側抽出に使われるが、[既存MCP運用文書](ai-import-mcp.md)はMCP候補機能がこのフラグに依存しないと記載する。`AI_IMPORT_ENABLED` のoffだけでMCPの停止を保証するとは扱わない。PR #192は別途、候補送信RPCに事業所別の既定off制御を追加した。

## データフローと責任分界

1. 職員が紙/PDFを外部AIクライアントに提供し、そのクライアントが読み取る。原本の保存場所、地域、保持期間、二次利用、削除とアクセスは当該サービスの契約・設定に依存し、未確認。CareRecord側で原本を削除しても外部側の削除を保証できない。
2. MCPの `list_workspaces` は所属事業所、`get_record_form` はフォームと接続本人のスタッフ名を返す。組織名や氏名も個人・組織の情報として扱う。対象の絞り込みは本人認証と所属の検証を要する。
3. `submit_record_candidate` は読取結果、警告、申告ファイル名を候補として送る。本文・氏名・日時など機微情報を含み得る。候補はCareRecord DBに保存され、管理者が原本と照合して承認するまで確定記録ではない。候補や原本の保持・削除はそれぞれの保存先の規程に従う。
4. 将来の参照・変更ツールではAIクライアントへの出力により別のデータ流出経路が生じる。提供先、出力項目、保存・再利用と操作の責任を機能別に再評価し、既存3ツールの利用可否から推定しない。

上記はリポジトリの実装・文書に基づく設計上の流れで、接続先や運用設定の実測結果ではない。

## 事業所・機能ごとの提供前チェック（提案）

各機能・事業所・環境・外部AI提供先の組合せごとに、判定責任者、判定日、対象バージョン、根拠の所在、未解決事項と再確認日を記録する。いずれかが未確認・不適合ならNo-Goとし、有効化しない。

- データ分類、取扱目的、送信対象・最小項目、提供先と再委託先、地域を確認する。自由記述、画像、添付、識別子、ファイル名は必要性を個別に評価する。
- 契約上の処理条件、保存地域、保存・削除期間、ログ保持、学習・二次利用、事業者や利用者によるアクセス、事故時対応を確認し根拠を保管する。
- 対象者への説明・必要な同意、事業所の導入判断と利用規約、権限の責任者を確認する。法務上の要否は担当者が判断する。
- 本人・所属・ロール・担当範囲を検証し、事業所外・失効・権限変更後・同名対象を拒否する。内容・件数を含む一覧、詳細、候補検索の漏えいを検証する。
- 機能別の上限、ページング、最小応答、機密項目の除外、エラーの安全化を定め、合成データで応答・ログを検査する。
- 停止・再開の責任者、操作手順、反映時間、監視、障害時連絡と代替業務を確認する。監査・否定試験・ステージングでの実測証跡を確認する。

例外の承認やリスク受容は既存の正式な意思決定・リリース手順に従う。未確認項目を本書だけで承認済みにしない。

## 制御・停止の方針

- 環境全体の緊急停止と事業所別・機能別の許可を分け、個人情報を扱う新機能は既定offとする。設定なし、無効値、設定取得失敗、対象不明は拒否する。認可・RLSをフラグで代替しない。
- MCPサーバーでツール実行前に判定し、DBの対象RPCでも同じ条件と本人・事業所・ロールを検証する。発行済みMCPトークンでPostgREST等からRPCを直接呼び出しても回避できないことを検証する。リスト・詳細・件数を含む全経路に適用する。新たなservice role経路は作らない。
- 既存OAuth接続の解除は更新トークンの失効を伴うが、発行済みJWTは期限まで有効な可能性がある。停止時にはトークン失効だけに依存せず、実行時のサーバーとDBの制御が必要。反映時間、同時実行中の取扱い、障害時の制御、再開時の再審査は設計・試験を要する。
- 停止は新規取込・外部送信を止める目的であり、既存候補・記録・監査の削除を伴わない。停止中も既存権限に従い候補の閲覧・照合・承認を維持する。通常業務と保持方針は変更しない。
- フラグの変更は認可された責任者のみが行い、対象環境・事業所・機能・理由・実行者・日時・結果を監査する。記録本文、原本、ファイル名、トークン、秘密情報はログに出さない。監査に失敗した場合、設定変更もロールバックする。

## 実装の範囲と残件

migration `20261027000001` は `submit_mcp_candidate` のDB内に事業所別の既定off制御を追加し、直接RPCを含む新規送信を拒否する。無効化RPCは有効なセッションと `integrations` 管理権限を検証し、設定更新と監査を原子的に行う。適用時は既存事業所を含め新規送信が初期状態で停止する。既存候補の確認・承認は変更しない。

事業所の連携管理権限を持つ管理者が提供先・処理条件・保存地域・保持・二次利用・利用者説明の6項目を確認し、根拠を入力して有効化できる。本人・有効セッション・権限をDBで再確認し、確認者と日時、設定変更を記録する。監査には自由記述を含めない。入力内容はシステムが事実確認できず、契約等の確認は管理者の責任である。根拠欄に記録本文、個人情報や秘密値を入力しない。外部AIへの原本の添付・送信は本機能より前に行われ、停止機能の制御対象ではない。

## 検証とロールアウト

ローカル合成データで、off・未設定・不正・制御参照失敗、別事業所、退会・失効、権限変更、直接RPC、onからoffへの切替をテストする。停止時に書込みと外部送信が発生しないこと、既存候補が維持されること、レスポンス・アプリ/基盤ログ・監査に合成の本文や秘密値が出ないことを確かめる。既存 `mcp_role_security.sql` の最小権限検査も維持する。ログ収集先と外部AI側の保持は各運用環境で別途確認する。

2026-10-27にPR #192をmainへ統合し、migration `20261027000001` をステージングと本番に適用した。本番はmigration履歴と対象テーブル・RPC、再dry-runで適用済みを確認した。CLIの適用後の補助カタログ保存では証明書ファイル不存在の警告が出た。適用時の新規MCP候補送信は全事業所で既定offである。各事業所の管理者が提供条件を確認しない限り有効化しない。

ステージングの合成データ専用事業所では、画面でoff→on→off、変更監査、on時の実MCP候補送信、off時の送信拒否と停止後の候補保持を確認した。試験後はoff。ローカルではDBテスト、unitテスト、送信と停止の並行試験、buildが成功し、PR #192のCIは全チェック成功した。これらは外部AI側の保持や提供条件の確認を意味しない。本番の認証済み画面と実データによる送信は試験していない。

既存接続中の利用者には候補送信の停止や作業中断が生じ得るため、提供責任者が実環境の状態と対象事業所を確認し、通知、代替手順、ロールバックと停止時の支援窓口を用意する。本番接続先・配備ソースの照合はPR #191に記録したが、外部AIの提供条件と事業所ごとの判断は未完了であり、#169の完了や新たな個人情報取扱いのGo判定とはしない。
