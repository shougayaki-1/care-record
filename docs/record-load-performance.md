# 提供記録の詳細表示（Issue #107）

## 読み込みの順序

既存記録は、利用者・テンプレート・スタッフ・交通費既定値・サービス種別・役割と、記録本体の取得を並列開始する。記録本体取得後、本文・実績スタッフ・月跨ぎ判定用シフト・`auditReportView` を並列実行する。全て成功してからフォームを表示する。読み込み・認可・本文監査に失敗した場合はフォームを表示せず、固定メッセージと再試行を表示する。本文行の欠落は既存の空回答として扱うが、DBエラーを空回答として編集させない。

画像は本文表示後に `getReportImages` を実行する。この Action 内の認可・署名URL生成・`report_image.view` 監査が成功してから表示する。遅延中・失敗時は画像欄だけに状態と再試行を表示する。再試行・アップロード後は画像だけを再取得し、編集中の本文を上書きしない。補助シフトの Server Action も本文表示後に開始し、本文閲覧監査の前にキューへ投入しない。

ユーザー・事業所・利用者・記録・シフト・区間・draftKey を読み込みscopeに含め、離脱・切替時は世代/cleanupで古い結果を破棄する。再読み込みが成功した後も前の世代の画像を表示しない。マスタ・本文・署名URLの永続キャッシュは追加していない。権限失効や事業所切替を跨ぐキャッシュの導入は今回の範囲外とし、毎回RLSとActionの認可を検証する。RLS・permissions・監査Action自体の変更はない。

## 計測

ブラウザの User Timing に固定名だけを記録する。`record-load:base` / `report` / `values` / `actual-staffs` / `audit` / `images` が各取得段階、`ready` が初期化、`body-visible` が初期化開始からフォームを含む次のanimation frameまでの時間。取得結果、ID、氏名、本文、署名URLは記録・送信しない。同名の過去measureを消し、各段階1件だけ保持する。クリックからルーターのマウントまでの時間は `body-visible` に含まれないため、ブラウザ側でクリック前に時刻を取得して別に計測する。

```js
performance.getEntriesByType('measure')
  .filter(entry => entry.name.startsWith('record-load:'))
  .map(({ name, duration }) => ({ name, duration }))
```

変更前後を同じ端末・ブラウザ・buildモード・合成データ・通信条件で比較する。ベースは `99a966f1b47bfc9f4ec38b89a50d657736a28a79`。専用ローカルSupabaseを使用し、E2EはAGENTS.mdの実行前確認後に実施する。旧版の段階内訳が必要なら計測用worktreeへ同じ固定名の計測だけを追加し、比較対象の動作は変えない。

- 一覧の「詳細」/「確認・修正」クリック直前から、回答が入り、編集対象の入力・承認ボタンが操作可能になるまで測る。承認済みは本文が表示されるまで測る。
- 初回表示とwarm表示を分け、同一利用者の別記録・異なる利用者・戻る→次の記録・直接URLを比較する。
- 画像0枚/3枚、通常回線/モバイル相当回線を比較する。各条件20回以上測り、ソート後の `ceil(n * percentile) - 1` の値をp50/p95とする。外れ値・失敗試行を黙って除外しない。
- Network/Performance traceからDB/API/Action/描画時間を確認する。traceには機密データが含まれ得るため、合成データだけで採取し、PRには固定名の所要時間と集計だけを残す。
- 画像取得だけを遅延・失敗させ、本文・承認操作が待機しないこと、再試行で本文編集を失わないことを検証する。`report.view` と `report_image.view` の監査件数・対象を専用DBで照合する。
