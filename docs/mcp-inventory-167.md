## 安全ゲートと後続契約

[システム方針](system-decisions.md) §9は、AI記録インポートを処理条件・保存地域・ログ保持・利用者説明の確認完了までフラグで無効とする。一方、[MCP運用文書](ai-import-mcp.md) は既存MCP候補機能が `AI_IMPORT_ENABLED` に依存しないと明記し、現行Edge Functionと候補RPCにも同フラグ参照はない。現行本番設定・利用条件は未確認。この差異を #169 のGo/No-Goに戻し、承認済み方針を優先する。資料がない現時点では新たな個人情報取扱いの提供判定はNo-Goとし、既存機能の実稼働状態は未確認として扱う。ここでフラグや配備設定を変更したり、既存機能が停止中と判定したりしない。

OAuth JWTの `mcp_import` ロールは `submit_mcp_candidate` の実行権限を持つため、Data APIからRPCを直接呼べる。Edge Functionだけを無効化しても候補登録を遮断できない。`AI_IMPORT_ENABLED` はNext.js側の設定で、Edge FunctionやDBへ自動的に共有されない。#169ではDB側のfail-closed制御も含め、既存候補の確認・承認を停止中に維持するか、組織別設定の正本・変更権限・監査・復旧を決める。接続解除のみでは発行済みJWTを即時無効化できると仮定しない。

新規ツールの名前、入力・出力、最大期間・件数、ページング、エラー型、事業所単位の停止手段、運用責任者は未確定。#168/#169/#171 のゲート後、各機能Issueで以下を具体化する。

- 本人と事業所・担当範囲を毎回サーバー側で検証し、利用者指定IDを認可根拠にしない。候補が複数なら自動決定しない。
- 保存時刻UTCと業務日Asia/Tokyoを区別し、境界を試験する。検索は限定された期間・件数・安定した順序とページングを持つ。
- 読取と変更のツールを分離し、最小属性・機械可読エラー・クライアントの発見可能な説明を定める。0件と失敗を区別し、エラーに機微情報を含めない。
- 変更は提案、明示確認、権限と版の再検証、監査を #170 で設計する。既存3ツールの互換性と段階的停止・ロールバックを試験する。
- 個人情報の外部送信・新機能公開は、#169の提供条件判定と必要なレビュー、合成データによる否定試験の完了まで行わない。
