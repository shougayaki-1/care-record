# MCP による記録変更と訂正案

`get_record_edit_template` は、現在の記録本文・版・日時・サービス・担当者を認可範囲内で取得し、閲覧監査を記録します。`prepare_record_edit` は現在の版を指定して変更後の項目と理由を送ります。案の作成だけでは記録を変更しません。日時、サービス、担当者を変更する場合は `changes` に指定し、省略したものは現在の値を維持します。フォームの型と選択肢、スタッフ別交通費、担当者の所属を検証し、担当者名はサーバーで解決します。

案は事業所・本人・OAuth 接続・元の記録・版・表示する名称とフォームに結び付けられ、10 分で期限切れになります。本人が CareRecord の画面で対象と変更前後を確認します。確定時には認証、接続、権限、対象、版、フォーム、担当者やサービスを再確認します。MCP トークンでは確定できません。

- **下書き**: 本人の確定後、既存の `save_report_versioned` で保存します。版競合を拒否し、保存・監査・案の消費は同一トランザクションです。
- **承認済み**: 本人が確認した訂正案を別に保存します。承認済み記録・現在版・承認状態は変更しません。訂正や再承認が完了したとは扱いません。保存済みの案は作成者が「記録一覧 → 保存した訂正案」から閲覧でき、元の記録やフォーム等が変わった場合はその旨を表示します。接続解除後も現在の閲覧・編集権限がある本人はアプリから参照できます。

機能は事業所ごとに既定で停止します。管理権限を持つ事業所管理者が取扱条件と根拠を確認して有効化し、記録参照も別途有効である必要があります。有効化・停止と監査は同一トランザクションです。AI 連携の停止後、確定前の案は実行できません。

変更前後の記録本文や理由は提案の保存と本人確認画面に必要な範囲で扱います。MCP 実行ログと監査の詳細には本文を含めません。提案は物理削除せず保持します。`record_versions` と既存監査を変更・削除しません。

実装と本番利用は別の判断です。DB migration は後方互換性を保ち、Staging・Production の順に手動適用します。本番前に対象・履歴・dry-run・バックアップ鮮度を確認し、アプリと MCP 関数の配備後も事業所の設定を自動で有効化しません。実施した検証と未実施の実認証試験は PR に記録します。

標準フォームはアプリと MCP の既存テンプレートに合わせて DB の関数に保持しています。標準フォームを変更する場合は新しい migration で `private.mcp_record_edit_default_schema()` を更新し、`mcpRecordEditDefaultSchema.test.ts` で一致を確認します。適用済み migration は変更しません。外部 API の確認は Context7 の Supabase DB 関数・実行権限と Next.js App Router の認証・非同期 `params` を 2026-11-08 に参照しました。
# 記録日の整合性

開始日時が日本時間で別の日に移る更新では、検索用の `service_date` も同じ更新内で揃い、通常の記録履歴に保存される。この動作は既存の記録更新にも適用される。migration 自体は既存データを書き換えない。
