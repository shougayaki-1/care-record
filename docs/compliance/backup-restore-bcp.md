# バックアップ・復旧・BCP

通常のアプリ配備の切り戻しは [デプロイ手順](../deployment-runbook.md) を参照します。アプリ配備を戻してもDBのmigrationやデータは戻りません。DB・Storageの障害と復元は本書の対象です。

## 目標

この文書は、通常運用の障害時に「提供記録表を10分以内に提示する」ための退避設計と、本番障害・誤削除・改ざんに備える保全設計を分けて定義します。

- 即時提示目標: バックアップ検索から提示まで数分以内
- 許容データ損失（限定提供中のRPO）: 最大14時間
- 復旧時間（RTO）: 最大4時間
- 不変保全: 法令・監査・事故対応のための長期保持

復旧目標は医療・介護業務への影響評価と顧客合意後に確定し、SLAと一致させます。

## 採用方針

- 退避先の第一候補は Google Cloud Storage
- 直近参照用は Standard、古い世代は Nearline または Archive
- 削除・置換防止は Bucket Lock を使う
- AWS を採る場合は S3 Standard-IA と Object Lock を同等候補とする
- 初期提供ではJPEG/PNG/WebPから安全化した記録画像だけを扱い、Supabase Storageを正本、非公開GCSを非同期複製・復旧用の副本とする
- 記録ファイルのGCS正本化とPDF/HEIC添付は提供開始後に実施し、それまではPDF/HEICを記録へ添付できない

## データ区分

- 即時検索用エクスポート: 提供記録表の検索・提示に必要な列のみを含める
- 不変バックアップ: DBや監査証跡の保全用
- 法定保持: 記録種別ごとの保持年数と法的根拠を別途管理する

## 即時検索用エクスポート

- 詳細な列定義は [backup-export-schema.md](backup-export-schema.md) に分離する
- 毎日1回以上、事業所単位で自動出力する
- 形式は CSV か JSON を基本とし、検索しやすい索引ファイルを同梱する
- 含める項目は利用者名、日付、サービス種別、提供時間、担当者、加算、備考を最低限とする
- 出力先は暗号化済みのオブジェクトストレージとする
- 実地指導時は、まずこの退避データを検索して提示し、DB復旧は最終手段にする

## 必須構成

- Supabase Freeの標準バックアップやPITRには依存せず、12時間ごとの完全論理DBバックアップをgzip圧縮してGCSへ保存する
- 失敗時は30分後、2時間後に再試行し、最新成功世代または対象データ最大更新時刻が14時間を超えた場合はCritical通知する
- 直近24時間はStandard、日次35日はNearline、月次370日はArchiveで保持する
- Auth全損時はユーザー情報と所属を復元し、全利用者へパスワード再設定を要求する
- Supabase Storage画像は保存後にGCSへ非同期複製し、復元時はmanifestの件数・サイズ・ハッシュ・記録との関連を照合する。GCS複製は初期提供時の正本ではない
- 本番管理アカウントと論理分離された別アカウント／保管先へ暗号化バックアップを保存する
- ランサムウェアを想定し、変更不能期間またはWORMを設定する
- 鍵、Migration、環境変数名、DNS、Vercel設定、Google連携復旧手順を同時に保全する
- バックアップ成功だけでなく、欠落・遅延・容量・改ざんを監視する
- 退避データの索引検索はバックアップ復旧を待たずに行えること
- 月次で退避データからの検索試験と提示試験を行うこと

## 復旧試験

提供開始前に1回、以後は月次で隔離環境へ復旧し、件数、代表レコード、Storage画像、記録ハッシュチェーン、認証、組織分離を照合します。実測RPO/RTO、検索開始から提示までの時間、失敗、是正期限、承認者を`backup_restore_tests`へ記録します。本番データを試験に利用する場合は同等のアクセス制御と終了後消去を行います。

## 非常時運用

サービス停止時は利用事業所が承認済み紙様式または隔離された代替手段で最小限の記録を継続し、復旧後に入力者、作成時刻、転記者、転記時刻を明示して登録します。未承認の個人クラウド、私物メール、メッセージアプリは使いません。
