# MCP 変更操作の安全契約（設計案）

状態: **案・未実装**（Issue #170、2026-10-28）。この文書は公開の許可やコンプライアンス達成の証跡ではない。承認済みの [system-decisions.md](system-decisions.md) を優先し、#167 の実接続先、#168 の本人・事業所・担当範囲、#169 の外部 AI 提供条件、#171 の契約試験・監視を確認するまで変更系ツールを公開しない。既存の `submit_record_candidate` は記録の確定ではなく確認待ち候補を作る既存機能であり、この案を実装済みと見なさない。

## 実装の基点と不足

- `save_report_versioned` は期待版と記録保存の冪等キーを受け、競合時は `CR409` を返す（`src/app/actions/reports.ts`）。記録の版と訂正履歴を迂回しない。
- `transition_reports_authorized` は記録の事業所・承認権限と状態を確認するが、現行引数には確認済み版がない。`transitionReports` の成功監査は RPC 後に別呼び出しであり、これだけで更新と監査が同一トランザクションと判断できない。
- `updateShiftTimeOnly` や `toggleCancelShift` は更新後に外部同期と監査を呼ぶが、期待版を条件に更新していない。既存操作をそのまま MCP から呼ぶだけでは本契約を満たさない。
- `recordAuditEvent` は追加専用監査の書込みエラーを送出するが、業務更新後の別リクエストでは既に確定した更新をロールバックできない。重要操作の監査 fail-closed には、更新と成功監査を同じ DB トランザクションに入れる設計が必要。
- `approve_ai_import_candidate` は候補行をロックし、承認者の事業所・記録権限を確認して記録保存と状態遷移を行う既存の画面用 RPC。#170 の本人確認済み提案、対象の版固定、重複実行時の共通契約を実装したものではない。

## 1. 提案: 副作用なしで対象と差分を固定する

提案の生成前にも本人認証・所属・担当範囲と閲覧権限をサーバーで検証する。クライアント指定 ID は認可信頼境界にしない。応答は許可された情報だけに限定し、対象 ID と同名識別に必要な表示、変更前・変更後、影響件数、対象範囲、操作種別、対象の版、Google 同期などの副作用、提案期限を示す。秘密・セッショントークン、不要な記録本文や他事業所の情報を返さない。

サーバーは事業所・本人・操作・対象 ID の集合・各対象版・正規化した変更内容・副作用・有効期限を改ざんできない提案に結び付ける。対象を問い合わせ条件だけで保存し、実行時に条件へ新たに一致した対象を無断で増やさない。複数対象の件数上限と個別版は操作ごとに決める。提案作成は業務データを変更しない。

## 2. 人による明示確認

AI の文章、ツール引数の `confirmed=true`、モデルの自己申告、チャット履歴だけで人の確認を証明しない。CareRecord の認証済み画面を確認経路の基準案とし、本人が固定された内容・対象・影響を見て明示操作する。MCP クライアントの確認 UI を採用する場合も、CareRecord サーバーが本人・表示内容・確認操作の真正性を検証できる実装と試験が必要。検証できない場合は画面で確認するか変更を拒否する。

確認証明は本人・認証 session・事業所・提案の固定内容に結び付け、サーバーの時刻で短期失効、単回消費とする。MCP や AI が確認証明だけを任意の対象に使い回せないこと。期限、保存方式、明示的な拒否・キャンセル、複数クライアント間の扱いは実装前に決定する。証明や提案内容を URL やログに含める場合は漏えいを避ける設計・検証が必要で、認証情報を AI に返さない。

## 3. 確定と並行操作

確定時には同一 DB トランザクション内で本人・OAuth 接続と失効状態、事業所所属、対象ごとの現行操作権限と担当範囲を再確認する。権限変更・退会・接続解除・担当変更と競合しても順序が確定するよう、関係する更新経路のロック順を設計し、待機後に期限を再検査する。

確認証明が未使用・未失効であり、本人・session・提案内容に一致することを検証し、対象の現在版と状態を再読込する。版の不一致、対象変更、削除・移動、権限喪失、確認内容のすり替えは拒否し、再提案と再確認を要求する。更新、版検証、確認の消費、重要操作の成功監査を同一トランザクションに置き、失敗時は全部ロールバックする。一括操作は原則全件成功か全件失敗とし、部分成功を採用する場合は別途その表示・監査・再試行を設計する。

記録作成・承認は正本の冪等規約を維持する。同一提案の重複送信は二重実行せず、認可を再確認した上で確定済み結果を返す。異なる内容で同じキーを再利用した場合は拒否する。タイムアウト後は安全に同じ操作の結果を照会できるようにし、失敗と成功不明を区別する。その他の更新は正本に従って楽観ロックを基本とし、確認証明の単回消費と結果照会は再実行防止のために別途必要とする。

## 4. 外部同期・監査・エラー

Google 障害時は DB のシフトを正本として保存し、未同期を明示して後から再実行する（[system-decisions.md](system-decisions.md) §8）。外部 API 呼び出しを DB トランザクションに含めて原子性を仮定しない。確定と同時に必要な同期状態を保持し、再送時の重複と障害復旧を個別操作ごとに設計・検証する。外部同期の成功を待たず DB 保存が成功した場合は、成功と未同期を両方示す。

追記専用監査に実行者、事業所、操作、対象、変更した項目名・件数など本文を含まない差分要約、確認・実行結果、相関 ID を記録する。記録本文、AI プロンプト、秘密、認証証明、生の DB エラーは監査や診断ログへ複写しない。重要操作の成功監査が書けなければ更新を確定しない。拒否・失敗監査は情報最小化し、失敗した業務トランザクションとは別の記録経路や監視を設計する。ユーザーには拒否・競合・再確認・同期保留を区別できる安全な文言を返し、未確認の成功を表示しない。

## 5. 公開前の検証と未決事項

#171 の契約試験で、確認なし、期限切れ、別本人・session・事業所、差分や対象のすり替え、退会・接続解除・権限変更・担当変更後、対象の版競合を拒否することを確認する。二重送信、同時確定、通信断後の再試行、監査書込み失敗、Google 同期失敗、一括対象の部分失敗を合成データで検証する。RLS と `permissions.ts`、既存画面、OAuth クライアントの双方で権限昇格がないことを調べる。#171 で拒否・失敗・同期保留・監査障害の監視と停止手順を用意する。

未決: 確認証明の TTL と保管・消費方法、確認を担う具体 UI、操作種別ごとの対象版と一括上限、結果照会の保持期間、監査イベントの詳細フィールド、Google 再同期の重複排除、対象更新と認可変更のロック順、確認証明発行後の OAuth 再認証・接続解除時の振る舞い。各実装 PR で脅威と業務影響を検討し決定する。利用者に表示する変更前後のデータを外部 AI に返す可否は #169 の確認結果に従う。
