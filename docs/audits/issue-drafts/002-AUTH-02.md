# AUTH-02: 重要操作RPCでstep-up再認証を強制する

Source finding: `docs/audits/authentication.md` / Severity: P1

## Background
owner移管、組織削除、calendar disconnectは高い影響を持つため、Action経由だけでなくDB境界でもstep-upを保証する必要がある。

## Current behavior
Server Actionはreauth grantをconsumeするが、authenticatedから直接呼べるRPCはactive session、owner、management permission、tenant boundaryを検査してもgrantを検証しない。

## Root cause
reauthenticationをActionの前提条件として実装し、SECURITY DEFINER RPCの直接呼出しに同じ検証を束縛していない。

## Scope
`transfer_owner_atomic`、`soft_delete_organization`、`update_organization_setting('calendar_disconnect')`の3操作と、そのAction/RPC契約を扱う。

## Out of scope
一般権限の再設計、MFA導入、Google OAuth全体の再設計。

## Security considerations
既存のactive session、owner、management permission、tenant boundaryを維持する。RPCを無防備と表現せず、step-upだけを迂回できる点を解消する。grantのuser/session/purpose/期限/一度限りを守る。

## Acceptance criteria
- 3 RPCがgrantなし、別purpose、期限切れ、使用済み、別sessionを拒否する。
- 正しいgrantを持つAction経路は従来の認可条件を満たす場合に成功する。
- 直接RPCとActionの成功・失敗・監査結果が同じ契約になる。

## Required tests
owner/非owner、管理権限有無、別tenant、grant状態別のRPC直接試験とAction回帰。並行consumeと失敗時の副作用も確認する。
