# 記録から履歴までの更新経路

Issue #34で通常・内勤・AIの永続化後の反映を統合。#32の入力UI、#33で扱う非同期通知・再試行・入力リセットは変更しない。

## 統合前

- 通常: `useRecordForm` → `saveReport` → versioned RPC → 画面遷移後に各ページのeffectで取得。
- 内勤: `InternalWorkDialog` → `saveInternalWork` → INSERT → 親の独自`loadRecords`。初期取得は別effectで、cleanup後の開始済みrefにより開発モードで停止する問題があった。
- AI読み取り: 入力候補を反映するだけで永続化しない。通常の保存へ合流。
- AI一括取込: 同じ`saveReport`で下書き保存するが、完了後は取込画面の行stateだけを更新。
- 外部AI送信: `ai_import_candidates`へ受信 → 管理者の承認RPCで通常記録に変換。履歴では候補を通常記録と別に描画し、常に先頭に表示。
- 内勤は本人の履歴・カレンダーに含まれなかった。

## 統合後

1. 通常保存、内勤保存、AI一括保存／候補承認・却下、既存記録の承認・差戻し・削除は`commitRecordChange`を通る。
2. 永続化の成功後だけ、組織IDをキーとして`refreshRecordFeeds`が購読中の一覧を再取得。一括保存は成功行がある場合にバッチ終了時の1回。取得失敗が保存済みの処理を失敗扱いにすることはない。
3. 履歴・内勤一覧・下書き一覧・管理一覧は`useRecordQuery`を利用。検索・組織ごとにスナップショットを丸ごと置換し、古いリクエストの応答を破棄。cleanupで購読と旧リクエストを無効化する。
4. 本人の履歴は`getMyRecordFeed`で既存の本人担当記録、本人担当の内勤、本人が送った未承認AI候補を集約。既存の所属・権限判定とsession client/RLSを利用し、管理者でも本人の内勤履歴に他スタッフ分を混ぜない。
5. `buildRecordFeed`で種別＋IDの重複を排除。記録開始日時の降順、同日時は種別＋IDで安定ソート。日付範囲は全経路で開始を含み終了を含まない。取得上限は各ソース100件、統合後100件。
6. リスト・カレンダーは同じデータを使用。`RecordFeedCard`が共通の日時・作成者・状態を描画し、内勤時間とAI確認待ちはメタデータ差分で表現。通常／承認済みAIの詳細は既存の通常記録画面へ遷移する。内勤には既存仕様上編集詳細がなく、候補は管理者確認待ちなので編集リンクを追加しない。

AI承認RPCは既存のトランザクションで通常記録を作成し、候補を削除する。再取得後は通常記録カードだけが残る。通常・AIの下書きは既存ルールどおり履歴へ出さず、記録作成の下書き一覧へ反映する。

## 外部変更と制約

ページへ戻った時はfocus／visibilityで共通取得を実行。外部AI送信にはブラウザ内の保存callbackがないため、本人の履歴は表示中に30秒ごとの同じ取得経路を使う。ブラウザの別タブからの変更もこの周期または復帰時に反映される。Realtime publicationや新しい永続キャッシュは追加しない。即時の更新通知は同じブラウザコンテキスト内の購読が対象。
