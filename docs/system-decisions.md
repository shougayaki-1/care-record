最終更新: 2026-09-23

## 位置付け

本書は、提供開始に向けて確定したシステム上の意思決定の正本です。実装、テスト、運用設定、ほかの設計文書が本書と矛盾する場合は、本書を優先し、矛盾を解消します。法令・契約・組織体制に関する判断は本書の対象外です。

本番提供の判定は [release-readiness-checklist.md](release-readiness-checklist.md)、日常の配備は [deployment-runbook.md](deployment-runbook.md) を参照します。[implementation-gap-plan.md](implementation-gap-plan.md) は2026-07-16時点の差分計画であり、現在の配備・CI手順は本書とrunbookを正とします。

## 1. リリース原則

- Criticalは受容せず0件にする。Highは原則解消し、理由、代替策、承認者を記録した`accepted-risk`だけを例外とする。提供条件は「Critical 0件、未解決かつ未受容のHigh 0件」とし、accepted-riskは最終判定で一覧表示する。accepted-riskに再評価日や有効期限は要求せず、それらの未設定・経過だけを理由にGo判定を拒否しない。
- 最初は少数事業所への段階提供とする。Supabase Free利用中は可用性の数値目標を設定せず、障害の検知・記録・利用者への通知だけを行う（改定 2026-07-16。FreeにはSLAがなく、目標値を掲げても制御できないため）。
- 正式提供前に、有料基盤への移行と可用性目標（99.5%以上）の設定を再評価する。
- 認証回避、他組織データ閲覧成功、要配慮個人情報の漏えい、監査ログ改ざんを検知した場合は、対象機能またはサービスを緊急停止できる。
- 脆弱性が見つかっただけではサービス全体を自動停止しない。可能なら該当機能の停止や暫定防御を行い、Criticalは原則24時間以内、Highは7日以内に修正する。

### 初期提供時のaccepted-risk

| リスク | 受容理由 | 主な代替策 | 承認者 |
|---|---|---|---|
| MFA未導入 | 初期提供では招待制と重要操作再認証を優先するため | 招待制、ログイン試行制限、重要操作再認証、セッション失効 | 提供責任者 |
| パスワード8文字・漏えい照合なし | Supabase標準と利用しやすさを優先するため | パスワードマネージャー許可、試行制限、アカウント列挙防止 | 提供責任者 |
| 無操作24時間・絶対30日 | 現場の継続利用を優先するため | 重要操作再認証、他端末失効、共用端末の保持禁止 | 提供責任者 |
| Supabase Free | 少数事業所への限定提供で実需要を確認するため | 容量安全弁、外形監視、独自バックアップ、段階提供 | 提供責任者 |
| 基盤アクセスと監査の非強制連動 | 利用基盤ではコンソールアクセスとの強制連動ができないため | アプリ内閲覧機能なし、GCSへのアクセス前後記録 | 提供責任者 |
| マルウェア検査未導入 | 初期提供では対応形式を安全化可能な画像に限定するため | 形式限定、シグネチャ照合、再エンコード、元ファイル非保存 | 提供責任者 |

## 2. 環境分離と基盤

| 環境 | Supabase | Vercel（想定） | データ | 用途 |
|---|---|---|---|---|
| Development | Supabase CLIによるローカル環境 | なし | 合成・ダミーデータのみ | 日常開発、マイグレーション、単体・DB・E2E試験 |
| Staging | Supabase Freeの独立Project | `care-record-staging` の Preview | 合成・匿名化データのみ | 必要なホスト済みAuth・Storage・連携確認、復元試験 |
| Production | Supabase Freeの独立Project | `care-record` の `main` Production | 実データ | 限定提供、本番運用 |

- Supabase Project、Vercel Project、GCP bucket、OAuth認証情報、暗号鍵、Cron秘密情報、監査ログ、バックアップ先を環境間で共有しない。
- 常設の`staging` Git branchは要求しない。feature branchからPRを作り、`main`に統合する。
- Productionは`main`のVercel Git配備を使う。Stagingの既存Projectはfeature branch Previewと、ホスト済みサービスが必要な確認のために残す。ライブ設定の確認状態は[deployment-runbook.md](deployment-runbook.md)に記録する。
- 非本番環境からProductionのDB、Auth、Storage、GCSへ接続できないようにする。
- ProductionとStagingは東京リージョンを優先し、GCSの別系統バックアップは大阪に配置する。
- 本番の必須環境変数が未設定、不正、別環境向けの場合はデプロイまたは起動を失敗させる。ダミー値で継続しない。
- Supabase Freeの制約を前提とし、DB使用量300MBで警告、400MBで新規事業所登録と大量インポートを停止、450MBで新規記録作成を停止する。400MB到達までに有料化または別DBへの移行判断を行う。
- 既知リスク（2026-07-16追記）: Supabase Freeプロジェクトは約1週間アクセスがないと自動一時停止する。Stagingは停止を許容して試験前に復旧確認を行う。Productionは個人情報を読まない最小DB health queryを含む5分間隔の外形監視で停止リスクを下げるが、停止防止は保証しない。自動一時停止と復旧遅延は`accepted-risk`とする。
- 前提（2026-07-16改定）: 限定提供中のVercelはHobbyを使用する。Vercel Cronは各jobを1日1回以下とし、12時間ごとのDB完全バックアップなど日次を超える定期処理はGitHub Actionsで実行する。Hobbyの利用量上限に近づくか、必要な実行頻度・精度を維持できなくなった場合はProまたは代替基盤への移行を判断する。

## 3. 認証とセッション

- 無操作タイムアウトは24時間、絶対セッション期限は30日とする。
- MFAは初期提供では使用せず、代替策を伴う`accepted-risk`とする。
- パスワードは8文字以上とする。氏名等との類似判定、一般的・漏えい済みパスワード照合、複雑性強制、定期変更は行わない。
- パスワードマネージャーと貼り付けを許可する。
- パスワード変更・再設定、メールアドレス変更後は他端末の既存セッションを失効する。
- ログイン失敗はIPとアカウントの両方で段階的に制限する。
- 自由登録は許可しない。初期オーナーの管理されたセットアップと、72時間・1回限りのメールアドレス一致招待だけを許可する。再発行時は旧招待を失効する。
- メールアドレス変更は旧・新メール双方の確認と再認証を必要とする。

### 再認証を必要とする操作

- オーナー移管
- 組織削除の申請
- バックアップからの復元
- 暗号鍵・外部連携の秘密情報変更

ロール・権限変更、Google連携の追加・解除、PDF・CSV・ZIP出力は再認証を要求しない。通常の認可と監査記録は必須とする。

## 4. 認可とテナント分離

- Supabase RLSと認可DB関数を最終防御かつ認可の正本とする。
- 画面側の権限判定はメニューやボタンの表示制御であり、セキュリティ境界にしない。
- 通常業務のデータ操作からservice roleを排除し、秘密鍵はブラウザへ渡さない。利用はログイン試行制限、OAuth nonce、サーバー管理セッション、Supabase Auth管理、バックアップ・復旧・Storage画像複製、監査保全、削除候補dry-run、基盤障害対応に限定する。初期提供コードは物理削除経路を持たない。各利用箇所を目的、対象、入力認可、監査とともにallowlistへ登録し、allowlist外の利用をCIで拒否する。
- すべての操作で、セッション由来の本人、組織所属、操作権限、対象リソースのorganization_idを検証する。
- オーナーはバックアップ状況を標準で閲覧できる。カスタムロールにも独立した`backupStatus.view`権限を追加できる。復元権限とは分離する。
- super adminはアプリ内から顧客の記録本文・ファイルへアクセスする機能を持たない（改定 2026-07-16。開発者=super adminの個人開発では、アプリ内grant機構がセキュリティ境界にならないため、機能自体を作らない）。基盤調査が必要な場合は、アクセス前に理由、対象組織、予定作業、開始時刻を削除不能なGCS監査bucketへ記録し、終了後に実施内容、参照対象、終了時刻を追記する。コンソールアクセスとの強制連動はできないため`accepted-risk`とする。

## 5. データ整合性と版管理

- 複数テーブル更新はDBトランザクションまたは原子的RPCで実行する。
- 再送による二重登録を防ぐため、記録の作成・承認処理に冪等キーを使用する（改定 2026-07-16。全更新系への適用はやめ、二重登録が業務上致命的な記録系に限定する。その他は楽観ロックで防ぐ）。
- 同時編集はバージョン番号による楽観ロックを使用し、競合時に後勝ち上書きをしない。
- 承認前の記録は権限の範囲で編集できる。承認後は元データを上書きせず、訂正理由付きの新しい版を作成する。
- 各版は旧版、新版、訂正者、日時、ハッシュを保持し、PDF・CSVにも出力時点の版と訂正状態を示す。
- DBの日時はUTC、画面・帳票・業務日判定はAsia/Tokyoを使用する。日付だけの値は日付型で保持し、端末時刻を監査や期限の正本にしない。

## 6. ファイル保存と安全化

### 初期提供

GCS正本化・マルウェア検査・PDF/HEIC対応は初期提供の必須要件から外し、提供開始後に実施する（改定 2026-07-16）。初期提供では記録画像はSupabase Storageを正本とし、JPEG、PNG、WebPだけを受け付ける。10MB・最大画素数制限、MIME・シグネチャ・実デコードの照合、SharpによるWebP再エンコード、metadata除去を必須とし、元ファイルは保存しない。PDF、HEIC、GIF、SVG、動画は記録へ添付できない。画像処理ライブラリを重点監視し、マルウェア検査未導入は`accepted-risk`とする。

### 提供開始後のGCS正本化仕様

- 記録の画像、PDF、HEIC本体は非公開GCSを正本とする。Supabase Storageはアバター等の小容量用途に限定する。
- 閲覧時にサーバーで認可し、対象ファイル1件だけに5分間有効な署名URLを発行する。プレビュー・ダウンロードを監査する。
- 1記録あたり画像とPDFを合計20ファイルまでとする。
- JPEG、PNG、WebP、HEICは1ファイル10MBまで、最大辺4096pxとし、安全な画像へ再エンコードしてEXIF等を除去する。HEICはJPEGへ変換する。
- PDFは1ファイル20MB、50ページまでとする。JavaScript、フォーム、添付、外部リンク、埋め込みメディアを無効化し、安全化した表示データを使う。
- マルウェア検査サービスが利用できない場合、アップロードは拒否する。

## 7. PWA、下書き、キャッシュ

改定（2026-07-16）: 初期提供ではPWA・オフライン機能・暗号化下書きを提供せず、オンライン専用とする（既存Service Workerの除去処理は維持）。以下は将来PWAを提供する場合の確定仕様として維持する。キャッシュ制御（`private, no-store`）は初期提供でも適用する。

- PWAを提供するが、Service Workerがキャッシュできるのは静的なJS、CSS、アイコン、フォント、アプリ外枠だけとする。
- 記録、利用者、スタッフ、シフト、監査ログ、画像、PDF、CSV、API応答をオフラインキャッシュしない。
- オフライン時に既存の個人情報は表示せず、正式な記録確定を行わない。
- 入力中データはWeb Cryptoで暗号化してIndexedDBへ一時退避する。鍵はセッションに紐付け、保存完了、破棄、ログアウト、失効時に削除し、未復旧の下書きも24時間で削除する。
- 通信復旧後は利用者が内容を確認してから送信する。
- 認証後HTML、API応答、個人情報、署名URL応答は`private, no-store`とし、共有CDNへ保存しない。

## 8. 外部サービス障害時の挙動

| 障害 | 挙動 |
|---|---|
| AI | 通常の記録入力を継続する |
| Google | シフトを保存して未同期とし、後から再実行する |
| マルウェア検査（提供後に導入） | 利用不能時はファイルアップロードを拒否する |
| 監査ログ | 権限変更、削除、承認等の重要操作を拒否する |
| バックアップ | 通常業務を継続し、障害を通知する |

## 9. AIと初期提供機能

- AI記録インポートは、データ処理条件、保存地域、ログ保持、利用者説明の確認が完了するまで機能フラグで無効にする。
- Googleカレンダー連携は有効にする。
- バックアップ状況閲覧はオーナーと許可ロールへ提供する。復元はアプリ内機能として提供せず、基盤側の運用手順（手動記録付き）で行う（改定 2026-07-16）。
- オーナー移管は再認証付きで提供する。
- 組織削除は即時物理削除せず、取消可能な保留状態にする。

## 10. 監査ログ

- アプリ上で1年間検索可能とし、改ざん困難な外部アーカイブへ10年間保管する。
- ハッシュチェーンを週次で検証し、欠落、改ざん、外部保存失敗を通知する（改定 2026-07-16。外部アーカイブ送信は毎日のまま、検証のみ週次）。
- アーカイブは通常画面やsuper adminから削除できない。
- ログに記録本文、ファイル内容、パスワード、トークン、秘密情報を保存しない。
- 出力ログは実行者、組織、出力種別、対象期間、対象件数、日時、成功・失敗、セッション識別子を持つ。

## 11. バックアップと復旧

- 限定提供中はRPO 14時間、RTO 4時間を目標とする（改定 2026-07-16。正式提供または利用拡大時に4時間間隔・RPO 6時間への強化を再評価する）。Supabase Freeの標準バックアップやPITRには依存しない。RTO 4時間は、誤削除・破損・Production Project単体障害で、Supabaseの新規Project作成、GitHub Actions、GCS、Vercelが利用可能な場合に限定する。リージョン・複数クラウド障害は保証対象外でbest-effortとする。
- DB完全論理バックアップを12時間ごとにGitHub Actionsのcron workflowで実行し、gzip圧縮してGCSへ保存する。失敗時は30分後、2時間後に再試行し、手動実行経路も用意する。最新成功世代または対象データの最大更新時刻が14時間を超えた場合はCritical通知する。接続はSupabase FreeがIPv6直結のみでGitHub ActionsランナーがIPv6非対応のため、Supavisorセッションプーラー経由とする。
- 各世代はDB roles、schema・RLS・関数・trigger、業務データ、Auth schema、Storage metadata、画像inventory、migration一覧、秘密値を除く設定version、暗号鍵ID・所在情報、件数・サイズ・ハッシュmanifestを含む。
- 直近24時間分はStandard、日次35日分はNearline、月次370日分はArchiveで保持する。prefixと作成日時に基づくGCS lifecycle ruleで移行・削除し、最低保存期間より前の削除料金を生じさせない。
- Supabase Storageの画像は保存成功後にGCSへ非同期複製し、失敗をキューで再試行する。日次で件数、サイズ、ハッシュ、`storage_path`、記録ID、組織ID、削除・legal hold状態を照合し、不足を自動補完する。最新の完全同期が26時間を超えた場合はCritical通知する。同一内容はハッシュで識別し、重複保存しない。
- GCSファイルは上書きしない日時・ハッシュ付きobject名を使用し、不要なobject versioningによる重複を作らない。東京の本体とは別に大阪のbucketへ日次複製する。
- 監査ログはDBバックアップと別系統で短い間隔により追記保全する。
- 週次で復号、整合性、件数を自動検査し、提供開始前に1回、以後は月次でStagingを使ってDBと画像の関連を含む復元時間を実測する（改定 2026-07-16）。
- 復元環境ではメール、Google同期、AI送信を自動無効にする。
- Supabase Project全損時はユーザーID、メール、組織所属を復元し、全利用者へパスワード再設定を要求する。必要に応じてGoogle再認可も要求する。
- Freeの2 Project制限下ではStagingを緊急復旧先として兼用する。Stagingの合成データを破棄してProductionを復元し、整合性確認後に環境変数・ドメインを切り替える。復旧後、空いたProject枠でStagingを再構築する。Stagingには固有データや唯一の証跡を置かない。

## 12. 削除

- 初期提供では保持期限による自動削除を`dry-run`に固定する。
- 通常画面の削除は論理削除とし、自動物理削除は行わない。Storage/GCSファイルも自動物理削除しない。
- 法的・本人請求・契約終了等の物理削除はアプリ外の個別対応とし、対象、承認、legal hold、結果を監査記録する。
- 初期提供のアプリ・Cron・管理ツールは物理削除実行経路を持たない。
- 将来、保持期間が確定した場合に、30日間の復元期間後の物理削除を別途有効化する。
- アカウント削除申請時は即時ログアウト、ログイン禁止、所属・権限無効化、外部資格情報失効を行う。30日間取消可能とし、過去記録の参照整合性を維持する。

## 13. 性能、制限、レート制御

設計目標は1事業所あたりスタッフ50人、利用者500人、記録10万件、シフト10万件、同時20セッション程度とする（改定 2026-07-16。旧目標の記録100万件はSupabase Free 500MBに物理的に収まらず、容量安全弁が先に作動するため現実値へ変更。基盤移行時に再設定する）。Supabase Freeの容量安全弁を優先し、上限到達前に基盤移行する。

- 一覧・検索、通常保存: p95 2秒以内
- 主要画面初期表示: 一般的な4G回線で3秒以内
- PDF・CSV生成: 通常範囲で30秒以内
- Google同期: 同時1件でキュー処理

レート制限（改定 2026-07-16。全API共通基盤はやめ、以下に限定する）:

- ログイン試行: IPとアカウントの両方で段階的に制限する（§3の通り）
- PDF・CSV・ZIP生成: 毎分3回
- ファイルアップロード: 毎分10件

読取・更新APIの汎用レート制限は初期提供では設けない。制限超過は429で返し、監査・異常検知へ記録する。100同時セッション試験は行わないが、提供前にスタッフ50人、利用者500人、記録10万件、シフト10万件相当と同時20セッションで主要操作を計測する。試験データだけで容量安全弁を超える場合は、実収容件数へ設計目標を修正する。

## 14. UI・アクセシビリティ

- 初期提供の合格基準はキーボード操作（フォーカス制御含む）、コントラスト、入力エラーの読み上げの3点とする（改定 2026-07-16。WCAG 2.2 AA全項目の監査は正式提供時に実施）。
- 200%拡大、幅360px、色以外の状態表現は主要業務画面で確認する。
- 保存中、保存済み、未同期、失敗、競合を明確に区別する。
- メール、ブラウザ通知に利用者名、記録本文、画像、健康・介護情報を含めない。
- CSV式注入、ZIPパストラバーサル、PDFメタデータを無害化し、出力ファイル名に利用者氏名を含めない。

## 15. 変更、CI、監視

- 変更は`feature/*` branchで作業し、PR上で差分と結果を自己レビューしてから`main`へ統合する。個人保守の通常変更に2人目のレビュー担当者は要求しない。
- PRの基本CIはlint、型、単体テスト、本番build、service role利用検査を含む。DB・認可・UI・E2E等の重い検査は関連変更で実行し、条件付きjobの省略がmergeを妨げない固定名の最終判定を使う。依存監査とSBOM、秘密情報検査はPRまたは定期実行で維持する。現在のコマンドと選択条件は[testing.md](testing.md)に記載する。
- DB migrationはStaging、Productionの順に手動適用する。Productionではmigration history、dry-run、直近のbackup freshnessを確認し、動作中アプリと互換なschemaだけを先行適用してからPRをmergeする。
- 日常リリースの記録は候補SHA、関連check、migration適用結果、配備URL、最小の稼働確認をPRに残す。初回提供・重要変更は[release-readiness-checklist.md](release-readiness-checklist.md)の証跡を使う。
- DB変更は追加、移行、切替、旧構造削除の段階方式とし、旧・新版の後方互換期間を持つ。
- 危険な機能は機能フラグで停止でき、限定事業所から段階配信する。
- 認証失敗、権限拒否、別組織ID試行、5xx、応答時間、容量、バックアップ、監査保全、Cron、Google同期、ファイル検査、service role、CSP違反、利用量を監視する。
- 依存関係は週次確認し、lockfile、SBOM、段階配信を使用する。
- 秘密情報・暗号鍵は定期交換ではなく、漏えい疑い、別環境投入、権限者変更、安全性低下、外部サービス要求等のイベント発生時に交換する。

### 15.1 日常配備の順序

- 通常のアプリ配備はVercel Git連携に任せ、Production Branchを`main`にする。手動のアプリ配備workflowは使わない。
- E2Eは専用クラウドDBではなく、一時的なローカルSupabase環境で合成データを使う。Production資格情報をE2Eへ渡さない。
- `/api/health`外形監視、完全DB backup、backup freshnessは定期運用として配備経路から分ける。外形監視は1系統を使い、完全backupとfreshness検査を残す。
- Staging / Productionの接続、branch filter、環境変数、`main`のcheck rulesは外部サービス設定であり、確認状況を[deployment-runbook.md](deployment-runbook.md)に記録する。文書やローカル変更だけで有効化済みとは扱わない。
